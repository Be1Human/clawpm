# ClawPM 递归拆解协议

## 从问题树开始

按以下层级建树，不能先按技术组件平铺任务：

1. **结果根任务**：用户最终能够观察和验收的结果。
2. **阶段或问题分支**：达成结果必须依次解决的能力、风险或交付阶段。
3. **叶子任务**：一个 Agent 可以独立完成并验证的最小工作闭环。

领域只用于分类，`parent` 才表示工作分解，`deps` 只表示执行顺序。多个领域可以出现在同一结果根任务下。

## 逐层递归

对每个非测试任务依次提问：

1. 是否包含两个以上可分别交付或失败的结果？
2. 是否需要跨越多个明显不同的实现边界，或先调查未知问题才能动手？
3. 是否必须等待多个独立步骤完成后才能验证？
4. description 是否已经变成实现清单，而不是对单一结果的说明？
5. 验收标准是否只能笼统地说“整体可用”，不能直接给出复现步骤？

任一答案为“是”，该任务仍是分支，必须继续拆分。未知信息先拆成 `spike`/调查叶子；调查完成后再补充后续子树，不要把猜测写成大任务。

## 叶子准入条件

只有同时满足以下条件的任务才可领取：

- 只产生一个可观察结果，不含隐藏的“以及/然后/同时完成”。
- 明确改动或调查边界；能指出目标模块、接口、资产或待确认问题。
- `acceptanceCriteria` 可直接执行或观察。行为任务覆盖成功路径，并在适用时覆盖失败或边界路径。
- 写明验证方法；实现任务需要测试记录或测试子任务。
- `deps` 仅包含真正必须先完成的任务，且依赖图无环。
- 一个 Agent 可以在一次连续执行中完成实现、验证和证据记录，不依赖另一个未建档的工作包。

不满足任一项时，继续拆分，不得领取父任务“边做边拆”。

## 推荐拆法

优先按可验证的纵向闭环拆分：

```text
结果根任务
├─ 明确契约或消除关键未知
├─ 跑通最小可用闭环
│  ├─ 实现叶子 A
│  ├─ 实现叶子 B
│  └─ 测试叶子
├─ 补齐错误、边界与恢复路径
│  ├─ 实现叶子
│  └─ 测试叶子
└─ 端到端验收叶子
```

不要默认拆成“前端任务、后端任务、数据库任务、测试任务”的同级清单。只有它们各自能独立验收时才能作为叶子；否则应挂在某个可验证能力分支下。

## 写入前检查

- 本次需求只有一个 `parent: null` 的结果根任务；复用已有父任务时可以没有新根任务。
- 除结果根任务外，每个新任务都有有效 `parent`。
- 每个分支至少有两个有意义的子任务；只有一个子任务时通常应合并或继续分析。
- 所有叶子通过准入条件，所有分支保持未领取状态。
- 每个实现分支都有测试闭环，最终结果根下有端到端验收。
- 子任务 ID、父子引用和依赖引用有效，依赖图无环。

若检查失败，先修计划再开始实现。
